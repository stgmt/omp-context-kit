Field data that may be worth factoring into the scoping. This is observational data from real sessions, **not** a benchmark — it does not meet the Acceptance criteria above and is not offered as the deliverable. Posting it because it bears on *which* strategies the comparison list should cover.

## Method

105 OMP session JSONL files from a single Windows workstation, 2026-09-04 → 2026-09-10. Text blocks of `toolResult` entries only, tokenized with `tiktoken` / `o200k_base` — no character proxy, per the point made above about `ceil(chars / 4)`. 22,886 tool results, 0 parse errors, 18,218,168 result tokens total. omp 18.1.6.

## Why this bears on the scope

The four strategies listed for comparison are all read-shaped: structural reads, selectors, delegated readers, worker-written code. In this sample `read` is 16.5% of tool-result tokens while `eval` is 63%.

The cost profile there is different in kind. Individual eval results are small — the expense is call count: 11,030 calls, each one a separate assistant turn whose code and result stay in context for the remainder of the session. Near-zero per-result waste, high aggregate turn overhead.

That call count looks like a direct consequence of the shipped `prompts/tools/eval.md` contract:

> Work incrementally: imports → define → test → use, each its own cell.
> Parallelize *within* a cell with `parallel(thunks)`, not by batching.

That is a deliberate and defensible design for incremental debuggability. But it gives the kernel-cell path an accounting profile none of the four listed strategies share, and it is the majority of observed volume. A routing policy tuned on a benchmark that covers only read strategies would be tuned against ~16% of what this sample actually spends.

## Suggested addition to the comparison list

Kernel-cell granularity, under the same correctness oracle:

1. one cell per step (current shipped default);
2. batched independent probes in a single cell via `tool.<name>()`;
3. in-sandbox compression via `completion(model="smol")` before printing.

The interesting metrics for that axis are aggregate turns and cumulative context growth, not per-result size — which is exactly the primary-vs-aggregate distinction this issue is making, applied to a non-delegated strategy.

## Limits, explicitly

Observational; single machine, single user, one week. No correctness oracle, no baseline/alternative pairing, no primary/worker split, no cost, retry, or cache accounting. It measures tool-result text only — not paid input tokens. It therefore cannot show whether any of these tokens were *wasted*, only where they were spent. It is input to fixture and scope selection, nothing stronger.

Happy to share the extraction script if the raw distribution is useful for choosing fixtures.
